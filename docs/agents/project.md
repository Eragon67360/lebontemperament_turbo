## Backend: Supabase

- **Two projects**: production `website` and `website-staging` (production's structure with fake data, [supabase/staging](../../supabase/staging/README.md)). Staging, previews and Vercel's Development target use `website-staging` since 2026-10-07; production, the apps, edge functions and crons use `website` ([safety](safety.md#production-and-staging-databases)). `supabase/config.toml` holds the local CLI config.
- **Tables** (`packages/domain/src/database.types.ts`, regenerated with `npm run db:types`): `profiles`, `groups`, `concerts`, `events`, `event_documents` (files attached to events), `rehearsals`, `programs`, `projects`, `tours`, `cas`, `activities`, `notifications`, `push_devices` (the phones registered for pushes) and `ops_alerts` (production alerts for the superadmins, `check-ops-alerts`), `public_concert_pushes` (the app's concert pushes to visitors), `files` and `folders` (the old Storage explorer), `drive_folders`, `drive_index_nodes`, `drive_sync_runs`, `youtube_links`, `feature_flags`, `bug_reports`, `bug_messages`, `donations`, `donors`, `donation_receipt_seq`, `deliveries`, `delivery_recipients`, `delivery_devices`, `delivery_code_attempts`, `order_sales`, `order_products`, `orders`, `order_items` and `order_payments` (« Commandes », superadmins only, #695), `rehearsal_sync_logs`, `mailing_list_comparisons` and `mailing_list_exceptions` (the roster against the Google Groups lists), `document_collections` and `site_documents` (« Documents de l'association », with `content_revisions` keeping every edit), `general_assemblies`, `site_announcements`, `faq_items`, `joining_slots`, `site_settings`, and the `anniversary_*` CMS tables.
- **Enums**: `user_role` = `superadmin` | `admin` | `user`; `group_type` = Orchestre, Choeur complet, Tous, Hommes, Femmes, Jeunes/Enfants; `activity_type` for the admin activity feed.
- **Migrations**: `supabase/migrations/` (2025-01 → 2026-10, one timestamped file per change). They create the newer tables, each with row-level security enabled. **The core tables** (`profiles`, `concerts`, `events`, `rehearsals`, …) **predate the migration history**: their schema and RLS policies live only in the database (`supabase/staging/01_schema.sql` is the owner's dump of production's schema from 2026-10-07).
- **Edge functions** (`supabase/functions/`): `sync-rehearsals-from-calendar` (Google Calendar → rehearsals, scheduled with `pg_cron` + `pg_net`; OpenAI reads the events, `llm-extract.ts`), `sync-drive-index` (Google Drive → `drive_index_nodes`, nightly cron plus the admin's `POST /api/drive-sync`; setup in its README), `generate-concert-event-data` (fills a concert's event data for Google from the admin's text and the poster, with OpenAI; #328), `send-push-notification` (FCM, members), `notify-public-concerts` (daily concert pushes to the app's visitors, FCM topic `public_concerts`), `notify-bug-report` (pushes a new signalement to the superadmins and each answer to the other side, from a database trigger), `check-ops-alerts` (every 15 minutes: failed or stale syncs, failed cron jobs and `pg_net` calls, pushed to the superadmins' phones; #364), the delivery-round functions (`send-delivery-invitations` sends the one invitation SMS with the date, link and code ahead of delivery day; on the day `start-delivery-round`, `send-delivery-sms` and `send-delivery-complete-sms` only push to the phones linked in the app, and `check-eta-and-send-arrival-sms` pushes « 5 minutes » or, for recipients without the app, sends the only other SMS; `optimize-recipients-route`; SMS through `_shared/sms-gateway.ts`, Twilio through `_shared/twilio.ts` as fallback; #593), `redeem-delivery-code` (a recipient's code from the SMS links the app to their delivery, no account; #593), `purge-bug-screenshots` (removes the screenshots of signalements resolved over a year ago, before the daily `purge_expired_records()` deletes them; #355) and `purge-order-documents` (removes the order forms no live order points at any more, which SQL can't delete from Storage).
- **Types**: `npm run db:types` regenerates `database.types.ts` from the remote project (needs `SUPABASE_ACCESS_TOKEN`; the script writes through a temp file so a failed run can't wipe the committed types).
- **How migrations and functions reach production**: nothing in the repo automates it (no CI step, no script). Treat both as manual owner-approved operations ([release](release.md#supabase)).

## Known quirks

- **TypeScript versions differ on purpose**: the apps type-check with TypeScript 7 (`typescript@^7`); the root pins `5.9.3` because ESLint's parser (typescript-eslint) loads the root TypeScript and doesn't support 7 yet (measured on #417). Run type checks through `npm run check-types` (Turbo, per workspace).
- **ESLint 10 runs on an `overrides` entry**: `eslint-plugin-react` 7.37.5 (the latest) declares ESLint up to 9 as its peer, and `overrides["eslint-plugin-react"]` in the root `package.json` lets npm install it next to ESLint 10. Its React version auto-detection calls `context.getFilename()`, which ESLint 10 removed, so `packages/eslint-config/next.js` sets `react.version` to `"19"` by hand: bump it with the apps' React major. Drop the override once the plugin declares ESLint 10.
- **The pre-commit hook is light** (`lint-staged`: Prettier on staged files; no build, no version bump): see [workflow](workflow.md#the-pre-commit-hook).
- **CI's Flutter analyzer fails on errors only** (`flutter analyze --no-fatal-infos --no-fatal-warnings` in `ci.yml` and the Android workflow; #362 tracks the warnings), while the [quality gates](quality-gates.md) ask for no new analyzer issue in what you touch: read the analyzer's full output yourself.
- **Versions** live in `version.json` and both apps' `package.json` (bumped on the release PR with `npm run release:bump`); the mobile version is in `pubspec.yaml` (`3.0.0+169` on 2026-10-27, the same as `version.json`). The iPhone version freeze (`version.json`'s `iosVersion`, 2.0.140 from 2026-10-11) ended with 3.0.0+169 (d25c46f, 2026-10-20): the key is gone and every platform carries the release version; the iOS workflow and `scripts/bump-version.js` still honour it if it is set again ([release](release.md)).
- **Prettier runs with its defaults outside the apps**: `apps/website/.prettierrc` and `apps/admin/.prettierrc` load `prettier-plugin-organize-imports` and `prettier-plugin-tailwindcss` (root dev dependencies) for those two apps only; `packages/`, `scripts/`, `supabase/` and the docs get plain Prettier. `.prettierignore` skips shadcn's generated `components/ui/**`, `*.d.ts` and lockfiles.
- **Vercel builds from the repository root** (Root Directory empty, `turbo build --filter=website` / `--filter=admin`); the repository has no `vercel.json`, since the unread `apps/*/vercel.json` were deleted (99bc607, #366) ([DEPLOYMENT.md](../../DEPLOYMENT.md)).
- **`next dev` rewrites `apps/website/AGENTS.md`** (the Next.js notice block): commit it with your work rather than fighting it.
- **Music, PDFs and videos are not in git** (#344). They live in the public Supabase Storage bucket `site-media` of the production project (free plan: 1 GB storage, 5 GB egress shared with the database; uploaded with a one-year cache header). The old URLs (`/music/...`, `/pdf/...`, `/videos/...`, used by shipped apps) are 308 redirects from route handlers (`apps/website/app/{music,pdf,videos}`, `lib/media.ts`). `lib/mediaManifest.json` lists every file, its object key and checksum; `scripts/media/media.mjs` rebuilds the manifest, uploads (`--apply` writes to production) and verifies. The files stay in git history at the manifest's `sourceCommit`. To add a media file, upload it to the bucket and add it to the manifest; don't put it back in `public/`. The 61 KB album cover stays in `public/music/BT - Album/` because `next/image` optimizes it from the tree. Tracks 16 to 27 of the anniversary album are listed on the page but were never in git (404 before and after).
- **Association documents are managed in the admin** (« Documents de l'association », migration `20261008233000_site_documents.sql`). The members area and `GET /api/documents` (website, also for the app with a bearer token) list `site_documents` by collection; each document's address is `/documents/<collection>/<file>`, a redirect to its file in `site-media` (admins upload straight from the browser under `documents/`, PDF only, 25 MB). Archiving hides a document; only superadmins delete. Until the migration is applied, the members area falls back to `public/json/pdf_files*.json`. From the next app release (#620) the app's Archives tab reads `GET /api/documents` as the member (every collection but `textes`, which the Règlement tab covers) and falls back to its built-in list in `pdf_archives.dart` and the `/pdf/...` links when offline or signed out; earlier app builds only have that list.
- **The general assembly page is managed in the admin** (Association › « Assemblée générale », migration `20261008233100_general_assemblies.sql`). `/ag` shows the newest published `general_assemblies` row (Markdown texts, convocation and proxy PDFs linked from « Documents de l'association »), the home page announces it until its day (Paris time), `/ag-2026` redirects to `/ag`. Until the migration is applied, `/ag` shows the 2026 AG (`LEGACY_ASSEMBLY` in `apps/website/lib/generalAssemblies.ts`).
- **Announcements are managed in the admin** (Concerts et site public › « Annonces », migration `20261009020000_site_announcements.sql`): the buttons under the home page's title (two at most at once) and the donation campaign card in the navigation (one at a time; its « already seen » key is per announcement, so a new campaign shows again). Each shows between its optional start and end days (Paris) and is decided in the browser. The card reads `GET /api/announcements` (cached 5 min, revalidated on save). Until the migration is applied, the card shows the hard-coded campaign (`LEGACY_DONATION_ANNOUNCEMENT`) and the home shows none.
- **The FAQ and the rehearsal times of « Rejoindre » are managed in the admin** (Concerts et site public › « Rejoindre et FAQ », migration `20261009020100_faq_and_joining.sql`): `/faq` and its FAQPage JSON-LD list the published `faq_items`, `/rejoindre` the published `joining_slots`, in the admin's order (both pages refresh every 5 minutes or on save). Until the migration is applied, they show `LEGACY_FAQ` (`lib/faq.ts`) and `REHEARSAL_SLOTS` (`lib/joining.ts`). The app's « Nous rejoindre » reads the same times from the public `GET /api/joining` (cached 5 min, revalidated on save; from the next app release, #620), with `kRehearsalSlots` as its fallback. The other joining facts are site settings (below); the app's `kJoiningFacts` are still in code.
- **Site settings are managed in the admin** (Concerts et site public › « Réglages du site », migration `20261012232052_site_settings.sql`, #621): the contact mailbox and registered office, the social links (one list for the footer, the floating bubble and the JSON-LD), the HelloAsso link and donation tiers of `/don`, the joining facts of `/rejoindre` and `llms.txt`, and the legal notice (publication director, phone, SIRET, registry). One `site_settings` row per key, checked by `@repo/domain/utils/siteSettings` in the admin's routes and on the website; the website reads them once per render (`lib/siteSettings.ts`, cached 5 min, tag `site-settings`, revalidated on save) and falls back per key to `DEFAULT_SITE_SETTINGS` while a row is missing or invalid. Only superadmins change the contact details (they route the contact forms and personal-data requests), in the API and in RLS. The contact-form routes read the mailbox from the settings too. The app's links are still in code.
- **Language**: the site, admin and app speak French to users; code, comments, docs and commit messages are in English (Conventional Commits).
